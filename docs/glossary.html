Glossary

Keywords, operators, and the programming-language theory behind them

Keywords

What every word means

Moss has no general-purpose keywords like var, function, or return. Every reserved word in the language was chosen to feel like part of a living system. Below is the full set, grouped by what they do.

grow Function declaration

Declare a function

grow introduces a named function with parameters and a block body. In PL theory this is a lambda abstraction — a binding of a name to a value that, when applied to arguments, evaluates its body in an extended scope. The name is bound in the surrounding environment so it can be called recursively.

sprout Variable declaration

Declare a mutable variable

sprout introduces a new binding in the current lexical scope and immediately assigns it a value via <~. Moss is dynamically typed, so no type annotation is needed — the variable can hold any value at runtime. Re-assignment later in the same scope uses <~ without sprout.

bloom Output statement

Print a value

bloom is a statement, not a function — it evaluates its argument expression and sends the result to standard output. It compiles directly to console.log(…) in JavaScript. Because it is a statement and not a value, it cannot appear as the right-hand side of an operator or assignment.

harvest Return statement

Return a value from a function

harvest is the early-exit mechanism for functions — equivalent to return. The static analyzer enforces that harvest can only appear inside a grow body; using it at the top level is a compile-time error. Combined with a guard clause it becomes a single-line early exit: n <= 1 => harvest n.

cycle While loop

Repeat while a condition holds

cycle is a head-tested loop: the condition is evaluated before each iteration, and the body runs only when it is truthy. It compiles to a JavaScript while loop. The optimizer can constant-fold the condition — a known-false condition eliminates the loop body entirely at compile time.

wither dormant Break / Continue

Exit or skip an iteration

wither terminates the enclosing loop immediately (like break). dormant skips the rest of the current iteration and continues with the next one (like continue). Both are structured jumps — they can only appear inside a cycle body. The static analyzer rejects either keyword outside a loop context at compile time.

when otherwise If / Else

Two-armed conditional

when … [~ … ~] is the standard two-armed conditional for blocks of code. The optional otherwise branch runs when the condition is falsy. For simple one-liner conditions, the guard clause => is preferred. The optimizer constant-folds when — if the condition is a known boolean at compile time, the dead branch is removed entirely.

colony Prototype object

Define a prototype object

A colony block creates a prototype record — a plain JavaScript object with named fields and methods. There are no classes, no constructors, and no new keyword. This is prototype-based OOP in the same spirit as early Self or Lua: objects are just objects, and inheritance is a matter of delegation, not class hierarchy.

grows Prototypal inheritance

Inherit from a colony

B grows [~ … ~] creates a new object whose prototype is B, then overlays the fields defined in the block. It compiles to Object.assign(Object.create(B), { … }). This is differential inheritance — you only specify what changes; everything else is looked up on the prototype chain at runtime. The analyzer checks that the left-hand side is a colony-typed value.

self Receiver reference

Refer to the current object inside a method

self is the equivalent of this in JavaScript or Python. It refers to the object on which the method is being called. The static analyzer enforces that self can only appear inside a colony method body — using it at the top level is a compile-time error. This is a contextual constraint enforced during semantic analysis.

graph Graph literal

Declare a first-class weighted graph

A graph [~ … ~] block is a graph literal — a compile-time structure that declares nodes and directed, weighted edges. The compiler validates that every node referenced in an edge declaration was declared with node. This is a static integrity check unique to Moss's type system.

spread reach BFS graph traversal

Traverse a graph breadth-first

spread G from start [~ reach current [~ … ~] ~] performs a breadth-first search starting at start, visiting each reachable node exactly once. The reach sub-block receives each visited node as current. It compiles to a while loop with a queue and a visited Set. The analyzer checks that the target of spread is a graph-typed variable.

Operators

The symbols and what they mean

Moss uses symbolic operators instead of words for its most structurally important operations. The direction of the arrows is not accidental — each points in the direction data or control flows.

<~ Assignment

Assign a value to a name

The arrow points left: a value flows from the right-hand expression into the name on the left. This mirrors mathematical notation where the destination comes first. Both sprout declarations and bare re-assignments use <~. The operator has the lowest precedence among expressions — everything on the right is fully evaluated first.

~> Pipeline

Pipe a value into a function

The arrow points right: a value flows from the left into the function on the right. x ~> f is syntactic sugar for f(x). Chaining is left-associative: x ~> double ~> show becomes show(double(x)). In PL theory this is reverse function application, popularized by F#, Elixir, and Elm — it lets you read a data transformation in the order it happens rather than inside-out.

=> Guard clause

Execute a statement if a condition is true

A one-armed conditional: if the left expression is truthy, the statement on the right executes; otherwise nothing happens and execution continues. This is semantically equivalent to if (cond) { stmt } in JavaScript, but without the syntactic noise. The optimizer constant-folds it — a literal true condition is eliminated, leaving only the statement; a literal false condition removes the entire guard.

[~  ~] Block delimiter

Open and close a block of statements

[~ opens and ~] closes every block in Moss — function bodies, loop bodies, colony definitions, graph literals, and conditional branches. The ~ on the inside keeps the delimiters visually distinct from all arithmetic and comparison operators. Unlike Python, indentation is not syntactically significant; unlike JavaScript, single-statement bodies still need delimiters.

-> Edge direction

Declare a directed edge in a graph

Used only inside a graph [~ … ~] block: edge A -> B weight N declares a directed edge from node A to node B with a numeric weight. Both nodes must have been declared with node earlier in the same graph block — the analyzer enforces this at compile time.

PL Theory

Concepts behind the compiler

Moss is compiled in four passes. Here is the theory behind each one and behind the more advanced language features.

Parse Phase 1

Grammar & PEG parsing

The grammar is written in Ohm, a PEG (Parsing Expression Grammar) library. PEG grammars are unambiguous by construction — each rule tries alternatives in order and the first match wins. Semantic actions in parser.js walk the parse tree and produce an Abstract Syntax Tree (AST): a tree of JavaScript objects where each node type corresponds to one syntactic construct (e.g. FunDecl, GuardStmt, PipeExp).

Analyze Phase 2

Scope, binding, and contextual constraints

The analyzer walks the AST and enforces rules that the grammar alone cannot express. It maintains a context stack that tracks: whether we are inside a function (to validate harvest), inside a loop (to validate wither and dormant), and inside a colony method (to validate self). It also checks that spread targets are graph-typed and that grows operands are colony-typed. These are static semantic checks — errors caught before any code runs.

Optimize Phase 3

Constant folding & dead code elimination

The optimizer performs constant folding: arithmetic on two known numbers is evaluated at compile time (2 + 3 becomes 5). Boolean short-circuits are collapsed. Guard clauses with a known-true condition become the consequent alone; known-false guards become empty. when and cycle statements with constant conditions are simplified similarly. Code after harvest, wither, or dormant in the same block is dead code and is dropped.

Generate Phase 4

AST-to-JavaScript code generation

The generator walks the (possibly optimized) AST and emits a JavaScript string. Each AST node type maps to a code template. The pipeline operator ~> becomes nested function application (f(x)). Guard clauses become if (cond) { … }. Colony declarations become object literals; grows becomes Object.assign(Object.create(…), { … }). Graph literals become a data structure; spread/reach becomes a BFS while loop with a queue and a visited Set.

Lexical scope Scoping

Names are resolved where they are written, not where they are called

Moss uses lexical (static) scoping: a name's meaning is determined by where it appears in the source text, not where the function is called from. A function body can reference names from its enclosing scope (closure), and those names are resolved at parse time rather than at runtime. The analyzer builds and tears down environment frames as it enters and exits scopes.

Dynamic typing Type system

Types are checked at runtime, not compile time

Moss is dynamically typed: variables have no declared type, and type errors surface at runtime rather than at compile time. The exceptions are the structural constraints described above — graph-edge integrity, colony/grows type pairing — which are structural static checks unique to Moss's domain types. Everything else follows JavaScript's runtime semantics.
